# Orion: why this fork is better

This fork is not just a cosmetic remix. It is a more practical, cleaner, and better-structured version of the original Orion-style UI library, built for real Roblox client work where window behavior, compatibility, and UX matter.

## Short version

This fork is stronger in the places that matter most:

- polished interface behavior instead of a basic static layout;
- clearer and more stable minimize/restore/close logic;
- mobile-friendly and touch-aware controls;
- searchable dropdowns and better widget responsiveness;
- clearer compatibility handling for restricted or partial Roblox hosts;
- cleaner project structure and docs that reflect the real source.

## Main differences from the original

### 1. Better window behavior

The original UI is functional, but the window lifecycle is often less clear when the user minimizes or closes it.

This fork improves the flow:

- minimize changes the window into a compact bar;
- the same control restores the full window;
- the close button on the minimized state destroys the UI completely;
- expanded close keeps the window hidden instead of breaking the user session.

This makes the library feel more stable and more like a real application window, not just a static panel.

### 2. Modernized controls

The fork adds or improves widget behaviors that feel more polished than the plain original versions:

- modern toggle switch with clearer visual state;
- mobile-friendly bind selector for keys and modifier combinations;
- searchable dropdowns instead of plain static lists;
- localized empty states for filters;
- cleaner labels and easier state restoration.

### 3. Better compatibility and safety

The source now warns in clear language when:

- it is required from the server instead of the client;
- the host blocks HTTP or `loadstring`;
- UI APIs or `PlayerGui`/`CoreGui` access is unavailable;
- the environment is not a normal Roblox Studio client runtime.

This makes debugging significantly easier because the failure message is explicit instead of cryptic.

### 4. Cleaner project layout

This repository keeps the actual library in `source`, while the site/demo content is kept separate from the real product. That is much easier to maintain than mixing the library code with a website or prototype UI.

### 5. Better documentation alignment

The docs in this fork are aligned with the actual code in `source` instead of describing a different or outdated version. This reduces confusion when you are integrating the UI into a real project.

## “Why this version is better” in practice

Compared to other Orion-style libraries, this version is stronger in a few concrete areas:

- faster to understand for new users;
- better UX for mobile and compact layouts;
- easier to debug in Roblox Studio;
- better UI control design and state transitions;
- more realistic support for runtime environments that restrict network or executor APIs.

This does not mean it is magically a complete desktop framework. It means the library has better real-world stability for common Roblox client use cases.

## Support for automation-style input environments

This project is intended for Roblox UI and client-side scripting. Some environments use automation layers, accessibility layers, or input-simulation wrappers that send synthetic clicks, key presses, or pointer events. This fork is designed to be more compatible with those kinds of environments when the host runtime allows them.

The relevant compatibility idea is:

- UI state should remain stable when input is generated by scripts, automation tools, or test harnesses;
- key and button controls should still work correctly even when the input source is not a human click;
- the UI should not assume that all input always comes from a direct user device event.

This is not a cheating tool and not a bypass system. It is a compatibility-oriented client library that handles script-driven and simulated input more gracefully when the environment permits it.

### Examples of supported compatibility patterns

- callback-driven UI controls that work with script-generated actions;
- keybind widgets that accept virtual or simulated input values;
- automation-friendly hooks for testing environments;
- input handling that stays consistent when mouse or keyboard events are recreated by a host framework.

This is useful for:

- UI testing tools;
- automation frameworks;
- accessibility or input simulation layers;
- internal QA environments that replay user events.

The key point is that the library must remain compatible with modern Roblox client execution models, not just with one narrow manual-input workflow.

## Recommended usage

Use this fork when you want:

- a clean and readable Orion-like UI library;
- better behavior for minimize and restore flow;
- support for mobile and touch-related interactions;
- stronger documentation and less API confusion;
- compatibility with automation-oriented input tools when allowed by the host.

## Summary

This fork improves the original Orion project in the places that matter most:

- usability,
- polish,
- compatibility,
- clarity,
- real-world client behavior.

That is why it is a stronger choice for production Roblox UI work and for environments that need more stable input handling.
